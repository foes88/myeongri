# 분석 결과의 버전 관리와 정정 이력

## 식별자
- `report_id`: 구매 단위 고유 ID. `revision`: 정정본 번호(1부터).
- 재현 키: `(input_hash, calculation_profile_id, engine_version, variant_id, ruleset_version, period, model_version, prompt_version)`.
  - `input_hash` = 출생정보 정규화 후 해시(솔트 포함, 원문 비저장 옵션에서도 유지 불가능하면 저장 안 함 → 재계산 불가를 고지).
- 구조 JSON(`structure_ref`)은 불변·콘텐츠 해시 고정. LLM 설명은 구조 JSON 해시에 종속.

## 재열람
- 구매한 보고서는 **당시 revision 그대로** 열람 가능(기본). 최신 정정본이 있으면 상단에 "정정본 있음" 배너.
- 엔진/규칙 업그레이드가 있어도 과거 보고서를 자동 재생성하지 않는다. 사용자가 "새 규칙으로 다시 보기"를 요청하면 새 report 로 만들고 두 결과의 차이를 diff 로 제공.

## 정정 절차
1. 오류 유형: 계산(만세력), 규칙(구조 판정), 문장(LLM 설명), 안전(금지 표현).
2. 신고 접수(`correction`) → 재현 → 영향 범위 조회(`ruleset_version`·`calculation_profile_id` 로 동일 조건 보고서 일괄 검색).
3. 수정 후 `report_revision` 추가, 변경 요약·사유 기록, 영향 사용자에게 알림.
4. **계산 오류**로 결론이 달라지면 무상 재발행 + 크레딧/환불 선택권(07 문서).
5. 사후 정정으로 과거 "적중/부합" 기록을 바꾸지 않는다. 상담 이력에는 정정 사실이 별도 이벤트로 남는다.

## 사후 끼워 맞추기 방지
- 상담 중 새 사건이 들어와도 `structure_ref` 는 바뀌지 않는다. 새 정보가 해석 조건을 바꾸면 **새 revision(상담용 해석)** 으로 분리 저장하고 변경 사유를 남긴다.
- "부합/불일치/애초에 판단하지 않음/조건 변경" 4분류로 이벤트 기록(Consult-Agent 설계, 아직 미구현).

## 하위 호환
스키마 버전(`schema_version`)을 모든 JSON 에 포함. 필드 삭제는 major 업그레이드에서만.
