작성: v6.6 §6 조사. 재현: `python -m tools.check_independent_pillars`, `python -m tools.check_tz_history` (임시 가상환경 필요, 아래 "재현" 참고).

## 1. 월주
월주 = (12절 절입 순간으로 정해지는 월 경계) × (오호둔 산술로 붙는 이름).

| 구분 | 결과 |
|---|---|
| 월 경계(절입 시각) 독립 계통 | JPL DE421(엔진) · 寿星(lunar-python, sxtwl) · **KASI 월력요항**(2004~2017 분 단위) · HKO(2026~28 분) · **VSOP87D**(celestial-calendar) · **KASI 특일정보 API**(korean-saju 내장 2000~2027) |
| celestial-calendar 절기 3600건(1901~2050) vs 엔진 | 최대 50.3초(1900년대), 1970년 이후 모든 10년 구간 최대 6초 이내, 60초 초과 0건 |
| KASI 월력요항 절기로 월·연주를 유도 vs 엔진 | 600건 무작위(2005~2016) 불일치 0 (절입 ±150초 제외). *(2015년 표의 입추가 "05시 1분" 한 자리 분 표기라 기존 수집기 정규식이 놓쳐 관대한 정규식으로 보충 — 공식 오기 아님)* |
| 월주 전체를 독립 구현이 산출 | korean-saju 600/600, bazi 600/600(+23시 규칙 2종씩), cnlunar 일 단위 466건 중 설명 안 되는 불일치 0 |
| **KASI 월건은 월주가 아니다** | 입춘(2024-02-04) 전후로 같은 음력 12월이라 월건이 바뀌지 않음 → KASI 월건은 **음력 월 기준**. 따라서 KASI 가 월주(절기 월)를 직접 제공하지는 않는다 |
| 월주 이름 산술(오호둔) | KASI 월건(음력월 기준)을 같은 산술로 재현: 달력자료 2023~2028 평달 72개월 + 변환 서비스 무작위 60건, 불일치 0 |

**판단**: 월 경계는 독립 계통 4~5개로 확인되었다. 월주 이름은 KASI 가 직접 주지 않으므로 ①오호둔 산술을 KASI 월건으로 확인하고 ②월주를 스스로 산출하는 **독립 구현 2종**(korean-saju, bazi)과 일치함을 확인했다. KASI 공식 자료만으로 월주 *문자열*을 직접 검증할 수는 없다(여전히 불가능).

## 2. 시주
| 요소 | 독립 검증 | 결과 |
|---|---|---|
| 균시차(진태양시 보정) | 가능 | 엔진(GAST−RA) vs celestial-calendar 1500건 최대 **0.003분**; vs bazi 진태양시 300건 최대 **0.33초**; vs NOAA 근사식 최대 0.90분(근사식 한계); 부호(시태양−평균) 일치 |
| 경도 보정(경도×4분) | 가능(산술) | korean-saju·bazi 모두 같은 산술. 서울 경도 126.9784(라이브러리) vs 126.978(엔진 표) 차이는 0.002분 미만. **도시 좌표 자체의 독립 검증은 하지 않음** |
| 시지 경계·오서둔 이름 | 가능 | korean-saju 600/600 (야자시 분리/통합 각각), bazi 600/600 (WAN_ZISHI/ZIZHENG 각각) 전 필드 일치 |
| 23시 규칙 | **불가능(정책)** | 라이브러리마다 선택이 다르다. 대응: ks 분리=MIDNIGHT_NEXT_DAY_STEM, ks 통합·bazi WAN_ZISHI=ZI_2300_DAY_CHANGE, bazi ZIZHENG=MIDNIGHT_SAME_DAY_STEM. 어느 쪽이 맞는지는 독립 자료로 정해지지 않는다 |
| 시간 보정 프로필 선택 | **불가능(정책)** | 아래 발견 참고 |

**발견 1 — 명칭 함정**: korean-saju 의 "진태양시(AST)"는 `KST + (경도−135°)×4분` 으로 **균시차가 없다**(= 우리의 평균태양시). 이름만 보고 진태양시와 비교하면 600건 중 시주 42건·일주 7건이 어긋난다(`contrast_*` 항목). 즉 균시차 포함 여부만으로 약 7%의 시주가 달라진다 — 철학관·앱마다 풀이가 갈리는 실제 원인이며, 프로필 변형을 병렬로 반환하는 현재 설계가 맞다는 증거다.
**발견 2**: 2000-01-01 19:25 서울의 진태양시는 18:49:39.8(bazi) vs 18:49:39.5(엔진) → 辛酉. docs/03 의 정정과 독립적으로 일치한다.

## 3. 대운 기산
3일=1년 환산은 **관습(프로필)** 이고 '정답'이 있는 계산이 아니다. 독립 구현이 일치한다는 것은 "같은 관습을 같은 방식으로 적용했는가"만 뜻한다.

| 구현 | 계통 | 비교(600건) |
|---|---|---|
| 엔진 | JPL, 360일 모델, 일 단위 내림 | 기준 |
| lunar-python Yun(sect=2) | 寿星 | 골든 10건에서 ±1일 일치(기존) |
| korean-saju Daewoon | KASI 데이터 | 순역 600/600 일치. 시작 나이(년·월): 엔진과 0개월 차 309건, +1개월 차 291건(월을 반올림 vs 내림, 1년=12개월 환산) |
| bazi dayun | VSOP87D 표 | 순역 600/600 일치. 첫 대운 시작일이 엔진과 ±4일 이내 600건(3일 이내 593건) |

**판단**: 독립 대운 구현이 이제 3종(寿星·KASI데이터·VSOP87D)이며 순역은 완전 일치, 시작 시점은 관습 허용 범위 내 일치. 다만 "시작 시점이 맞다"고 말할 근거는 없다 — 관습의 세부(반올림·1년 길이)를 선택한 것이다.

## 4. 시간대·서머타임 역사
열람한 출처(2차 공개 자료 3종): ko.wikipedia 「한국 표준시」, namu.wiki 「서머타임」 표, en.wikipedia 「Time in South Korea」. **법령 원문(대통령령·관보)과 KASI 공식 표준시 문서는 열람하지 못했다** (`primary_law_text_checked: false`).

| 항목 | 결과 |
|---|---|
| 표준시 전환일 1912-01-01(+9), 1961-08-10(+9) | tzdata 와 전환 순간까지 일치(MATCH) |
| 1908-04-01 (+8:30 최초 시행, 연혁 사실 예시) | 날짜 일치, 위키에 시각 서술 없음 (MATCH_DATE_ONLY) |
| **1954-03-21 (+9 → +8:30, 연혁 사실 예시)** | 날짜 일치, **전환 시각 30분 차이**: ko 위키는 +9 시계 00:30 에 되돌렸다(=03-20T15:30Z), tzdata 는 00:00(=15:00Z). 법령 원문 미확인 → **미해결** (영향: 1954-03-20 23:30~03-21 00:30 출생) |
| 서머타임 시작·종료 일시 (1948~51, 1955~60, 1987~88 — 24개 전환) | namu 표의 현지 시계 일시를 UTC 로 환산해 tzdata 전환 순간과 비교: **24/24 일치** |
| 서머타임 연도 집합, 1952~54 미시행, 1988 5/8~10/9 | 일치 |
합계 30개 사실: MATCH 28, MATCH_DATE_ONLY 1, DATE_MATCH_TIME_OF_DAY_MISMATCH 1. 이 출처들은 tz 데이터베이스나 같은 조사를 참조했을 수 있어 완전한 독립은 아니다.

## 6. `verification_levels` 에 대한 제안 (적용하지 않음)
1. **PILLARS_VERIFIED — 새 증거 반영(요건 완화 아님)**. 현재 규칙("네 필드 모두 독립 계통 2종 이상")에 `korean-saju`(KASI 데이터 계통)와 `bazi`(VSOP87D 계통)를 월·시 필드의 계통으로 추가하면 규칙상 충족된다. 단 ①새 라이브러리가 소규모·신규이고 ②VSOP87D 와 寿星의 이론 공유 여부 미확인이므로, 채택한다면 근거를 `independent_pillars_check.json` 의 *불일치 0* 에 연결하고 범위 문구("양력 입력, 시간 보정 프로필 선택은 별개")를 함께 표시할 것을 권한다.
2. **PROFILE_VERIFIED — 쪼개기를 제안**. (a) 메커니즘(균시차·경도 보정·시지·오서둔·일 경계 구현): 독립 확인됨 → 부여 가능. (b) 정책(어느 프로필이 맞는가): 검증 불가 → 계속 "변형 반환". (c) 시간대 연혁: 2차 자료 대조 28/30, 법령 1차 미확인, 1954 전환 시각 30분 불일치 → **계속 미부여**. 지금처럼 하나의 플래그로 두면 (c) 때문에 (a)의 진전이 보이지 않는다.
3. **DAEUN_VERIFIED — 쪼개기를 제안**. `DAEUN_DIRECTION`(순역: 독립 구현 3종 600/600 일치 → 부여 가능)과 `DAEUN_START_CONVENTION`(시작 시점: 관습이므로 '검증'이 아니라 '구현 간 허용오차 내 일치'로만 표시)으로 분리. 후자를 "검증 완료"로 표기하면 요건 완화이므로 하지 말 것.
4. **시간대 근거 문구 갱신**: "독립 자료와 대조하지 않음" → "2차 공개 자료와 대조(28/30 일치), 1차 법령 미확인, 1954 전환 시각 불일치 미해결". 이 문구 갱신만으로는 판정이 바뀌지 않는다. 2차 자료를 독립 근거로 *인정*하는 것은 정책 결정이며 요건 완화에 해당하므로 별도 승인이 필요하다.
5. 위 어느 것도 V1 을 열지 않는다: LUNAR/라이선스(KASI·HKO 이용 조건 미확인)/PROFILE(c) 가 남는다.

## 7. 하지 못한 것 / 한계
- 법령 원문(1954·1961 표준시 개정, 1987·88 서머타임 대통령령) 확인: 접근하지 못함.
- 도시 좌표(서울 126.978°E 등)의 독립 검증: 하지 않음.
- 23시(야자시/조자시) 규칙, 시간 보정 프로필 선택, 대운 환산 세부: 정답이 없는 정책/관습이라 검증 대상이 아님.
- korean-saju/bazi 의 코드 품질·장기 유지보수는 평가하지 않음. 서비스 런타임에는 넣지 않았다.
- 1962년 이전·2028년 이후 구간은 korean-saju 가 Meeus 폴백을 쓴다(그래도 일치했으나 KASI 데이터 직접 대조는 아님).

## 재현
```
python -m venv %TEMP%\indep_venv
%TEMP%\indep_venv\Scripts\python -m pip install cnlunar korean-saju bazi celestial-calendar==0.6.1
cd backend
python -m tools.check_independent_pillars      # 필요: data_private/external/{kasi_almanac,kasi_calendar}.json (tools.fetch_kasi_almanac / fetch_kasi)
python -m tools.check_tz_history               # 네트워크 필요 (ko/en wikipedia, namu.wiki)
```
`INDEP_VENV_PY` 환경변수로 가상환경 python 경로를 바꿀 수 있다. 가상환경과 `data_private/` 는 저장소에 포함되지 않는다.
